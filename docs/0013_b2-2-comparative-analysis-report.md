| **4) 트러블슈팅 문서화** | 4대 트러블슈팅 1:1 역할 분배, 시나리오 내 완벽 통합 | 표(Table)와 체크리스트로 깔끔하게 정리됨 | `stash -u` 등 예상치 못한 에지 케이스 리얼하게 반영 | 로직 버그 픽스와 겹쳐 Git 명령의 본질이 흐려지기 쉬움 |

| **6) 구두 평가 방어력** | What/Why/How 템플릿 강제화, ORT 메커니즘 설명으로 완벽 방어 | 체크리스트 기반으로 충돌 해결 논리가 단단함 | HEAD~1, 3-way merge 원리 등 본인들의 배운 점이 잘 서술됨 | 코드 로직 설명에 치중하여 Git 자체의 평가 방어가 약할 수 있음 |

## 3. 💡 주요 인사이트 및 Action Item (Takeaways)

### 🏆 우리 팀 시나리오의 압도적 우위점
1. **완벽한 리스크 통제 및 대칭성 보장**: Code-based 팀들이 겪는 "코드 머지 후 실행 에러(Syntax Error)" 리스크를 원천 차단하면서도, 평가 기준인 **1인당 PR/리뷰 횟수**와 **Request Changes 피드백 루프**를 시나리오(Step 501~509)에 기계적으로 맞물려 두어 감점 요소를 완벽히 제거했습니다.
2. **Git ORT 엔진에 대한 높은 이해도 어필**: 단순히 같은 라인을 고치는 수준을 넘어, 파일 이동(`git mv`)과 수정(Modify)을 동시에 일으켜 100% 비자명 충돌을 발생시키는 기법은 평가관에게 Git 머지 엔진에 대한 깊은 이해도를 어필할 수 있는 강력한 무기입니다. (Team 6도 유사한 방식을 썼으나 마크다운이 아닌 파이썬 파일로 진행하여 리스크가 있었습니다.)

### 벤치마킹을 통한 실무 적용 팁 (배울 점)
1. **Team 6의 "충돌 해결 체크리스트" 도입**:
   - Team 6은 충돌 해결 시 `[x] 양쪽 변경 의도를 확인했는가?`, `[x] 충돌 마커를 모두 제거했는가?` 와 같은 체크리스트를 PR 본문이나 문서에 활용했습니다. 
   - **적용 방안**: 우리 팀도 `docs/conflict-resolution.md` 작성 시 단순 서술에 더해 마크다운 체크리스트 양식을 첨부하면, 구두 인터뷰 시 "충돌 해결 프로세스를 어떻게 거쳤나?"라는 질문에 논리적이고 정형화된 답변을 할 수 있습니다.
2. **Team 9의 `git stash -u` 및 마크다운 백틱(```) 충돌 경험 방어**:
   - Team 9은 새로운 파일(Untracked file)을 stash할 때 일반 `git stash`로는 저장되지 않아 `git stash -u`를 사용해야 했던 현실적인 트러블을 기록했습니다. 
   - **적용 방안**: 김건우 님의 트러블슈팅(stash) 실습 시, 새로 만든 파일이 있을 경우 `-u` 옵션이 필요하다는 점을 구두 평가 대비용 멘트로 준비해 두면 좋습니다. 또한 마크다운 문서 병합 시 백틱(```)이 겹쳐서 문서 렌더링이 깨지는 현상이 빈번하므로, 머지 직후 반드시 VS Code의 "Markdown Preview" 기능으로 렌더링 이상 유무를 점검하는 단계를 추가해야 합니다.
