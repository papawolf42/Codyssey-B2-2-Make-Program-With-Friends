# 협업 가이드 (CONTRIBUTING)

## GitHub Flow 브랜치 전략 채택 이유 (3줄 요약)
- main 브랜치는 항상 오류 없이 배포 가능한 안정 상태를 유지합니다.
- 새로운 작업은 main에서 분기한 feature 브랜치에서 독립적으로 진행합니다.
- 모든 변경사항은 PR 템플릿 작성과 동료 리뷰 및 승인을 거쳐 머지합니다.

## 브랜치 및 커밋 규칙
- 브랜치명: `feature/<담당자>-<작업명>`
- 커밋 메시지: 무엇을 왜 바꿨는지 명확하게 서술 (update/fix 단독 사용 금지)

## PR 작성 및 코드 리뷰 규칙
- PR 본문에 What, Why, How와 `Closes #이슈번호` 필수 기재
- 리뷰어는 구체적인 라인/문장을 근거로 실질적인 질문 또는 개선 제안 작성
- 작성자는 답변 또는 코드 수정을 반영하고 재확인 후 머지

## 충돌(Conflict) 대응 및 해결 규칙
- **해결 주체 (누가 해결하나)**: 선병합자(먼저 main에 머지한 팀원)의 변경을 확인한 후, **후병합자(충돌을 만난 해결자 팀원)**가 로컬 브랜치에서 `git fetch origin` ➔ `git merge origin/main`을 실행하여 충돌을 직접 해결합니다.
- **검토 및 합의 (누구와 확인하나)**: 해결자는 임의로 한쪽 코드를 덮어쓰지 않고, **선병합자 및 지정 리뷰어와 함께** 두 사람의 작업 의도가 모두 보존되었는지 최종 diff와 마커 해소 상태를 확인한 후 리뷰 승인을 받습니다.
- **기록 보존 (어디에 기록하나)**:
  - 개별 증빙: `docs/evidence/conflict-<조코드>.md`에 실제 충돌 마커 원문과 해결 이유를 기록합니다.
  - 팀 종합: `docs/conflict-resolution.md`에 충돌 상황, 기준 커밋, 해결 절차, 배운 점을 본문에 통합합니다.
